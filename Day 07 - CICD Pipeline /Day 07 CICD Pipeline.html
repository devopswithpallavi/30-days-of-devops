01
The Problem — Manual Deployment Workflow
⏱ 0:22 – 4:02

Before CI/CD, teams followed a manual deployment process — error-prone, slow, and stressful. Nana explains that "a human in the loop" is the root cause of most of these problems.

Merge Conflicts
Developers worked in isolation for weeks. When merging, there were hundreds of conflicts — very hard and time-consuming to fix.
Code Freeze
Before a release, new code was blocked from being pushed — only bug fixes allowed. Team productivity completely stopped.
Manual Testing
QA teams manually tested everything — slow, error-prone, and impossible to scale with large codebases.
Late Bug Detection
Bugs were found after weeks of work — much more expensive to fix. Early detection = cheap fix.
Deployment Fear
Deploying was a high-stress event — because something always broke and had to be fixed manually under pressure.
😰 Old workflow: Weeks of coding → Big merge → Code freeze → Manual test → Pray → Deploy → Something breaks → Panic all night! CI/CD eliminates all of this.
02
What is CI/CD?

CI/CD stands for Continuous Integration / Continuous Delivery (or Deployment). It is an automated pipeline that handles everything from code commit to production deployment — removing manual, human-error-prone steps.

CI — Continuous Integration
Every code commit automatically triggers a build and test process. Bugs are caught early, before they reach production.
CD — Continuous Delivery / Deployment
After tests pass, code is automatically delivered to staging or deployed to production. The release process is fully automated.
💡 CI/CD's main goal: Remove "human in the loop" from repetitive steps — automate build, test, and deploy so engineers can focus on writing code, not managing deployments.
03
Continuous Integration — CI
⏱ 4:02 – 8:18

Continuous Integration means developers commit their code to a shared repository frequently — multiple times a day. Every commit automatically triggers a build and test pipeline. Bugs are caught within minutes, not weeks.

Frequent Commits
Developers push small changes daily to feature branches — no more weeks of isolated work. Merges become easy.
Automated Build
Every commit triggers an automatic build — compile errors are caught immediately without anyone manually checking.
Automated Tests
Unit tests and integration tests run on every commit — bugs are found within minutes, not after weeks of work.
Fast Feedback Loop
Developers know within minutes if their code broke something — the earlier a bug is caught, the cheaper it is to fix.
✅ CI Goal: "Always have a working, tested, deployable codebase." No more code freeze. The main branch is always stable.
04
Continuous Delivery — CD
⏱ 8:18 – 15:26

Continuous Delivery extends CI. After tests pass, build automation tools automatically create a Docker image and deploy it to a staging/testing environment — with zero manual steps. The code is always ready for production, but a human gives final approval.

Docker Image Build
After CI passes, a Docker image is automatically built — versioned and pushed to an artifact registry (DockerHub, ECR, etc.).
Deploy to Staging
The image is automatically deployed to a staging environment identical to production. End-to-end functionality is validated here.
End-to-End Testing
Full system tests run in staging — not just unit tests. Real user flows are tested before production release.
Manual Approval Gate
A human reviews the staging deployment and clicks approve or reject. This is the only manual step in the pipeline.
💡 Continuous Delivery = "Always ready to release." The code can go to production at any time — the human decides when, not how.
05
Continuous Deployment vs Continuous Delivery
⏱ 15:26 – 17:12

Nana clearly differentiates these two — they are commonly confused. The key difference is whether a human approves the production release or not.

📌 Most teams start with Continuous Delivery — manual approval gives a safety net. As test confidence grows, they move toward Continuous Deployment.
06
Deployment Strategies
⏱ 17:12 – 21:07

Even with CI/CD, deploying to production carries risk. Nana covers two key strategies to reduce risk during production releases — Canary and Blue-Green deployments.

🐦 Canary Deployment

New version is deployed to a small percentage of users first. Monitor for errors. If everything is good, gradually roll out to more users until 100%.

🐦 Why "Canary"? Coal miners used to send a canary bird into mines to detect toxic gas. If the canary died, miners stayed out. Same logic here — if the 5% deployment breaks, only 5% of users are affected. Roll back immediately and fix.

🔵🟢 Blue-Green Deployment

Maintain two identical production environments — Blue (current live version) and Green (new version). Switch all traffic instantly. If something breaks, switch back to Blue in seconds.

✅ Blue-Green's biggest advantage: Zero downtime + Instant rollback. If Green has problems, flip the traffic switch back to Blue in seconds. Fix Green and try again.
